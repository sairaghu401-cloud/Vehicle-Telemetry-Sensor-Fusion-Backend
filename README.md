# Vehicle Telemetry & Sensor Fusion Backend

[![CI](https://github.com/sairaghu401-cloud/Vehicle-Telemetry-Sensor-Fusion-Backend/actions/workflows/ci.yml/badge.svg)](https://github.com/sairaghu401-cloud/Vehicle-Telemetry-Sensor-Fusion-Backend/actions/workflows/ci.yml)

A backend that ingests live multi-sensor data (radar, ToF, GPS) from embedded devices,
fuses and validates it server-side, stores it for historical analysis, and exposes it
through a documented, secure API.

**Status:** Step 8 complete — project scaffold, Docker Compose stack, health check,
database schema with Alembic migrations, REST API, WebSocket live ingestion with
Redis current-state, radar/ToF sensor fusion with anomaly detection, auth
(per-device API keys for ingestion + JWT for the dashboard/REST API), and a
pytest integration suite covering fusion, auth, devices, and WebSocket ingestion,
and a GitHub Actions pipeline that tests, checks migrations, and builds the Docker image on every push.

## Stack

- **API:** Python 3.11 + FastAPI
- **DB:** PostgreSQL 16 (SQLAlchemy 2.0 async + Alembic migrations)
- **Cache / live state:** Redis 7
- **Real-time ingestion:** WebSocket
- **Auth:** API keys per device (ingestion) + JWT (dashboard/user access)
- **Containerization:** Docker + docker-compose
- **CI/CD:** GitHub Actions

**Why this layout:** each folder is organized by *what the code does*
(models, schemas, api routes, services), not by feature. At this project's
size that keeps related code near its peers — all DB tables in one place,
all endpoint definitions in one place — so as we add devices, readings, and
fused events in step 2+, they slot into existing folders rather than each
feature growing its own parallel mini-app.

## Setup

1. Copy the environment template and fill in real values (the defaults work
   fine for local dev — just don't reuse them anywhere real):

   ```bash
   cp .env.example .env
   ```

2. Build and start the full stack (API + Postgres + Redis):

   ```bash
   docker compose up -d --build
   ```

3. Check everything is healthy:

   ```bash
   curl http://localhost:8000/health
   # {"api":"ok","postgres":"ok","redis":"ok"}
   ```

4. Open the interactive API docs (auto-generated by FastAPI from the code —
   this updates automatically as we add endpoints):

   ```
   http://localhost:8000/docs
   ```

5. Stop the stack:

   ```bash
   docker compose down
   ```

   Add `-v` to also wipe the Postgres/Redis data volumes (useful if the DB
   gets into a weird state during development): `docker compose down -v`

## Database migrations (Alembic)

The schema is defined once, in Python, as SQLAlchemy models under `app/models/`.
Alembic compares those models against the live database and generates a
migration script — a version-controlled record of exactly how to move the
schema from one state to the next (and back).

Run migrations from inside the `api` container (recommended — it already has
the right Python env and can always reach `db` by hostname) or from a local
venv pointed at `localhost`:

```bash
# Apply all pending migrations (run this after `docker compose up` on a
# fresh database, and again any time a new migration is added):
docker compose exec api alembic upgrade head

# After changing a model, generate a new migration by diffing against the DB:
docker compose exec api alembic revision --autogenerate -m "describe the change"

# Then review the generated file in alembic/versions/ before applying it —
# autogenerate is a good first draft, not a guarantee. Then:
docker compose exec api alembic upgrade head

# Roll back the most recent migration:
docker compose exec api alembic downgrade -1

# See which migration the database is currently at:
docker compose exec api alembic current
```

**Always read a generated migration before running it.** Autogenerate is
good at detecting new/dropped tables, columns, and indexes, but it has real
blind spots:
- It can't tell a column rename from a drop+add — it'll generate a
  destructive drop-then-create pair unless you edit the migration to use
  `op.alter_column` instead.
- Postgres `ENUM` types are separate database objects from the tables that
  use them — dropping a table does not drop the enum type it referenced, so
  a generated `downgrade()` needs the enum drops added by hand (this project's
  first migration required exactly this fix — see the comment in
  `alembic/versions/..._create_devices_sensor_readings_fused_.py`).
- It has no idea about data migrations (e.g. backfilling a new required
  column) — those are always written by hand.

## Running the tests

```bash
# Postgres and Redis need to be reachable on localhost (the test suite
# talks to them directly, not through the api container) — the full stack
# or just the two dependencies both work:
docker compose up -d db redis

# From your local venv (see "Local development without Docker" above —
# pytest isn't installed in the Docker image itself, only requirements.txt
# is, not requirements-dev.txt, which is deliberate: a production image
# shouldn't ship test tooling):
pip install -r requirements-dev.txt
pytest
# or, to see each test name and its result:
pytest -v
```

**The tests use their own database (`telemetry_test`) and their own Redis
index, never your dev data.** `tests/conftest.py` points the app at
`POSTGRES_DB=telemetry_test` and `REDIS_DB=15` *before* any app module is
imported — see the big comment at the top of that file for exactly why the
ordering matters. Every test run drops and recreates `telemetry_test` from
scratch (via `Base.metadata.create_all`, not Alembic — these tests check
the schema matches the models, not that the migration scripts work), and
every individual test gets a clean slate (`TRUNCATE` + `FLUSHDB` after each
one). You can run `pytest` as many times as you want without ever touching
the devices/readings you've created manually while poking at the API by
hand.

What's covered:
- `tests/test_fusion.py` — pure unit tests of the fusion decision logic
  (no DB, no network — these run in milliseconds; see step 5).
- `tests/test_auth.py` — registration validation, login success/failure
  (including the anti-enumeration same-error-message behavior), and the
  `get_current_user` dependency protecting `/devices/*` (no token, a
  malformed token, a token for a since-deleted user).
- `tests/test_devices.py` — device registration/duplicates, 404 handling,
  and the paginated `/history` and `/fused-events` endpoints (pagination
  actually not overlapping across pages, filters actually filtering).
- `tests/test_ws_ingestion.py` — a real WebSocket handshake against the
  real app: a valid API key gets acked and durably stored, an invalid key
  is rejected at the handshake (before `accept()`), a malformed message
  gets an error ack without killing the connection, and ingesting a
  matching radar+ToF pair actually produces a fused event end-to-end.

These are genuine integration tests — real Postgres, real Redis, the real
FastAPI app wired together exactly as it runs in Docker — not mocks. That's
a deliberate tradeoff: slower than pure unit tests (seconds, not
milliseconds), but they catch the bugs that actually show up at the
boundaries between layers, which is where most of the real bugs caught
while building this project (see the design-decision call-outs throughout
this README) actually lived.

## Design decisions worth knowing about

- **Async SQLAlchemy (asyncpg) for the API, sync (psycopg2) for Alembic.**
  FastAPI's request handlers are async, so a blocking DB call would stall
  the whole event loop under load. Alembic runs as a one-off CLI command
  outside that event loop, so it doesn't need the added complexity of an
  async driver.
- **Settings via pydantic-settings, not raw `os.getenv()`.** One typed,
  validated config object catches env var typos at startup instead of as a
  silent `None` deep in request handling.
- **`docker-compose` mounts `./app` and `./alembic` as volumes with
  `--reload`.** During development, code changes on your host machine are
  picked up by Uvicorn immediately, without rebuilding the image. (We'll
  want a separate, non-reload, non-volume-mounted config for anything
  resembling production.)
- **UUID primary keys for `devices` and `fused_events`, plain auto-incrementing
  `BigInteger` for `sensor_readings`.** Devices register themselves and could
  in principle generate their own ID before ever contacting the server —
  UUIDs need no central coordinator. `sensor_readings` is the highest-volume,
  server-generated table, where a smaller, sequential, cheaper-to-index key
  wins and there's no independent-generation requirement to justify a UUID's
  cost.
- **Enum values stored lowercase in Postgres (`values_callable=...`), matching
  the Python `.value` and the future JSON API.** SQLAlchemy's default behavior
  stores the Python enum member's *name* (`RADAR`) rather than its `.value`
  (`radar`) — a mismatch that would otherwise force ugly case-translation
  between the database, the ORM, and the API's JSON. Worth knowing this
  default exists so it doesn't surprise you in a different project.
- **A composite index on `(device_id, recorded_at)` for `sensor_readings`
  and `(device_id, event_time)` for `fused_events`.** The main query pattern
  we'll build in step 3 is "give me this device's data in this time range" —
  a composite index lets Postgres jump straight to the relevant rows already
  sorted by time, instead of a full table scan.

## Auth

Every `/devices/*` endpoint now requires a logged-in dashboard user (a JWT
bearer token). The WebSocket ingestion endpoint (`/ws/ingest`) is
unaffected — devices keep authenticating with their own API key, not a JWT
(see "two separate auth subjects" below).

```bash
# 1. Register a dashboard user (one-time)
curl -X POST http://localhost:8000/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email": "you@example.com", "password": "a-strong-password"}'
# -> {"id": "...", "email": "you@example.com", "created_at": "..."}

# 2. Log in to get a JWT — note: this is form-encoded, not JSON
#    (OAuth2PasswordRequestForm calls the email field "username")
curl -X POST http://localhost:8000/auth/login \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "username=you@example.com&password=a-strong-password"
# -> {"access_token": "eyJhbGciOi...", "token_type": "bearer"}

# 3. Use the token on any /devices/* call
TOKEN="eyJhbGciOi..."   # paste the access_token from step 2
curl http://localhost:8000/devices -H "Authorization: Bearer $TOKEN"
```

In `/docs`, click **Authorize** (top right), enter your email/password in
the form that pops up, and every "Try it out" call in the docs UI will
include the Bearer token automatically — no need to copy/paste it
yourself.

## WebSocket ingestion

Devices push live readings to `ws://localhost:8000/ws/ingest?api_key=<device's api key>`.
One message = one sensor reading:

```json
{"sensor_type": "radar", "recorded_at": "2026-09-22T11:00:00Z", "distance_m": 4.2}
{"sensor_type": "tof",   "recorded_at": "2026-09-22T11:00:00Z", "distance_m": 4.35}
{"sensor_type": "gps",   "recorded_at": "2026-09-22T11:00:00Z", "latitude": 16.4419, "longitude": 80.6206}
```

Each message gets an ack back: `{"status": "ok", "reading_id": 124}`, or
`{"status": "error", "detail": "..."}` for a malformed message (the
connection stays open after an error — only a real disconnect or an
invalid API key ends it).

Try it with the included test client (no Node.js/npm required — just the
project's existing Python venv):

```bash
# From inside the api container:
docker compose exec api python scripts/test_ingest_client.py sk_live_your_key_here

# Or from a local venv pointed at localhost:
python scripts/test_ingest_client.py sk_live_your_key_here
```

It sends one reading of each sensor type and prints the server's ack for
each. If you have Node.js/npm and prefer an interactive session,
[wscat](https://github.com/websockets/wscat) (`npm install -g wscat`) also
works:

```bash
wscat -c "ws://localhost:8000/ws/ingest?api_key=sk_live_your_key_here"
> {"sensor_type": "radar", "recorded_at": "2026-09-22T11:00:00Z", "distance_m": 4.2}
```

Read a device's most recent reading (from Redis, not Postgres — this is
what a live dashboard would poll). This one's a REST endpoint, not part of
the WebSocket, so it does need the dashboard JWT (see **Auth** above):

```bash
curl http://localhost:8000/devices/{device_id}/live -H "Authorization: Bearer $TOKEN"
# {"device_id": "...", "latest_reading": {"sensor_type": "radar", ...}}
# or {"device_id": "...", "latest_reading": null} if nothing in the last 5 minutes
```

## Sensor fusion

Every time a radar or ToF reading is ingested over the WebSocket, the
server looks for a reading of the OTHER type from the same device within a
2-second window. If found, it fuses the two:

- **`ok`** — distances agree within 0.5m (`DISCREPANCY_TOLERANCE_M`)
- **`anomaly`** — distances disagree beyond 0.5m — worth a dashboard
  alert, since it means one sensor may be malfunctioning or something in
  the environment (a reflective/absorptive surface, etc.) is fooling one
  of them
- **`insufficient_data`** — currently unused by the automatic path (see
  design notes below) but available for a future manual/batch fusion mode

GPS readings never trigger fusion — cross-validation here is specifically
radar-vs-ToF distance agreement.

```bash
# All fused events for a device
curl http://localhost:8000/devices/{device_id}/fused-events

# Just the anomalies — the actual point of doing fusion at all
curl "http://localhost:8000/devices/{device_id}/fused-events?status=anomaly"
```

Run the fusion unit tests (pure logic, no database needed):

```bash
docker compose exec api pytest tests/test_fusion.py -v
# or from a local venv: pytest tests/test_fusion.py -v
```

## Design decisions worth knowing about — sensor fusion

- **Fusion logic is a pure function (`fuse_distances`), separate from the
  database-touching orchestration (`try_fuse_reading`).** The actual RULE
  — "given two distances, what's the status?" — has zero dependency on
  SQLAlchemy, async, or the database. This is what lets `tests/test_fusion.py`
  test the real business logic in milliseconds with plain numbers, and
  it's a pattern worth reusing anywhere "decide something" and "fetch/store
  something" can be pulled apart.
- **A real bug hit and fixed while building this: matching an
  already-consumed reading.** The first version matched "the most recent
  reading of the other sensor type within the time window" with no memory
  of what had already been fused. When same-timestamp readings arrived
  close together, a later reading could re-match a partner that an
  earlier fusion had already used, producing a spurious second
  FusedEvent for a pairing that was never actually simultaneous. Fixed by
  excluding any reading ID already present in an existing FusedEvent's
  `source_reading_ids` — verified by reproducing the double-count, fixing
  it, and re-running the same scenario to confirm exactly the right
  number of events was produced.
- **A fixed 0.5m tolerance, not percentage-based.** Simpler to reason
  about and tune. A percentage-based tolerance (tighter at close range,
  looser at long range) is more physically realistic for most ranging
  sensors and a reasonable future refinement — noted here rather than
  built now, to keep the first version's logic easy to verify.
- **No `INSUFFICIENT_DATA` event for a reading with no partner (yet).**
  Every reading eventually gets a partner or doesn't — creating an event
  for every single unmatched reading (extremely common: it's the normal
  state right after a device connects) would flood the table with noise.
  `INSUFFICIENT_DATA` in `fuse_distances` exists for a future manual/batch
  fusion mode that explicitly asks "fuse whatever we have as of now" and
  needs to represent a real gap; the automatic per-reading path simply
  does nothing until a partner shows up within the window.
- **The already-fused lookup is scoped per-device, not a full table
  scan — but still O(recent events), not O(1).** `source_reading_ids` is
  stored as a comma-separated string (see the field's own comment in
  `fused_event.py`), which means checking "has this reading been used
  already" means loading and parsing recent events rather than an indexed
  SQL lookup. Fine at this project's scale; if fusion volume ever grows
  large, a proper join table (`fused_event_id`, `reading_id`) would make
  this an indexed query instead — the same tradeoff flagged when
  `source_reading_ids` was originally designed in step 2.

## Design decisions worth knowing about — WebSocket ingestion

- **Auth happens before `websocket.accept()`, not after.** A WebSocket
  handshake is itself an HTTP request that gets upgraded. Rejecting a bad
  API key by calling `close()` before `accept()` means an unauthenticated
  client never gets a live connection — the same principle as a REST
  endpoint returning 401 without doing any real work.
- **One DB session per CONNECTION, not per message.** A device might send
  hundreds of readings over one connection's lifetime; opening a fresh
  session for each one would be far more overhead than the actual insert.
  This mirrors the connection itself being long-lived.
- **Redis is updated only after the Postgres commit succeeds.** Postgres
  is the durable source of truth; a reading is only advertised as "the
  current state" once it's safely persisted. Updating Redis first would
  risk a dashboard showing a reading that was never actually saved (e.g.
  if the DB write failed after Redis succeeded).
- **A malformed message doesn't close the connection — only a real
  disconnect does.** One corrupt sensor payload is data-quality noise, not
  a reason to force the device to reconnect and lose its whole session
  (analogous to how one REST 422 doesn't invalidate the client's whole
  session).
- **The Redis "latest reading" key expires after 5 minutes
  (`LATEST_READING_TTL_SECONDS`).** If a device goes silent, its last
  reading shouldn't be shown as "current" forever — after the TTL, `/live`
  correctly reports `null` ("no recent data") instead of a stale value
  that looks fresh.
- **Cross-field validation on the ingested message
  (`IngestReading.check_fields_match_sensor_type`).** Pydantic validates
  each field's type independently, but "distance_m is required when
  sensor_type is radar" spans two fields — this needs a model-level
  validator, and it catches a malformed device payload before it ever
  reaches the database, rather than silently storing a radar reading with
  no distance.

## Design decisions worth knowing about — API layer

- **Pydantic schemas, never raw ORM objects, cross the API boundary.**
  `Device` (the SQLAlchemy model) has an `api_key_hash` column; `DeviceOut`
  (the Pydantic schema) deliberately does not. Returning the ORM object
  directly would leak that hash into every response. Separate "In"
  (request) and "Out" (response) schemas also mean the database schema and
  the API contract can evolve independently — a common source of pain in
  APIs that skip this layer.
- **The raw API key is shown exactly once, at creation.** Only its bcrypt
  hash is ever stored. If a caller loses the key, there is currently no
  recovery — only issuing a new one (a natural addition once step 6 auth
  exists to gate who can do that).
- **Offset/limit pagination for `/history`, not cursor-based — with a
  known tradeoff.** `page`/`page_size` are simple to reason about and let
  a client jump to an arbitrary page number, which suits a
  time-range-filtered query most callers will use. Deep unfiltered paging
  (e.g. "page 50,000") gets slower under OFFSET because Postgres still has
  to scan and discard every skipped row — a cursor-based scheme (paging by
  `id < last_seen_id`) avoids that but can't jump to an arbitrary page. Not
  a problem yet at this project's scale; worth reconsidering if very deep
  unfiltered paging becomes a real use case.
- **A shared `_get_device_or_404` helper, not inline checks in every
  endpoint.** Every endpoint taking `device_id` needs the same "does this
  device exist" check — factoring it out means that behavior (including
  the exact error message) can't drift between endpoints over time.
- **`passlib` + `bcrypt` version pinning.** passlib 1.7.4 (last released
  2020) fails its own internal self-test against bcrypt's newer major
  versions — hit this directly while building step 3 (see the comment in
  `requirements.txt`). Pinned `bcrypt==4.0.1` explicitly rather than
  trusting `passlib[bcrypt]`'s unpinned transitive dependency.

## Design decisions worth knowing about — auth

- **Two separate auth subjects, two separate mechanisms — not one
  "auth system."** A *device* pushing sensor readings and a *person*
  viewing a dashboard are fundamentally different callers with different
  needs, so they're authenticated differently rather than forced through
  one shared scheme:
  - **Devices** (WebSocket ingestion) use a long-lived API key
    (`sk_live_...`), issued once at registration, sent as a query param on
    the WebSocket URL. No login flow, no expiry — a device isn't a person
    who can "log back in" if a token expires; it just keeps the key it was
    given.
  - **Users** (REST API / dashboard) use short-lived JWTs obtained via
    `/auth/login`, sent as an `Authorization: Bearer` header. This suits an
    interactive session where a person logs in, works for a while, and can
    log in again later.

  This is why adding auth touched two different dependencies
  (`authenticate_device_by_api_key`, already in place since step 4, and
  the new `get_current_user`) instead of one — and why `/ws/ingest` needed
  zero changes in this step.
- **Passwords are hashed with the same `passlib`/bcrypt setup as API
  keys** (`app/core/security.py`) — one hashing primitive reused for both,
  rather than a second hashing library. Same pin, same tradeoffs already
  documented above.
- **JWTs are signed, not encrypted.** Anyone can base64-decode a JWT and
  read its payload (`{"sub": "you@example.com", "exp": ...}`) — the
  signature only proves the server issued it and it hasn't been tampered
  with. Never put secrets (passwords, keys) inside a JWT payload; here it's
  just the user's email.
- **Short expiry, no server-side revocation (yet).** A stolen token is
  valid until it expires — there's no "log out everywhere" or blocklist.
  Keeping `jwt_expire_minutes` short bounds how long a leaked token stays
  useful. A real revocation scheme (a blocklist in Redis, or a "token
  version" column on `User` that invalidates all previously issued tokens
  when bumped) is a natural addition if this needs tightening later.
- **Login returns the same error for "no such user" and "wrong
  password."** Returning different messages (or different status codes)
  for each would let an attacker enumerate which emails are registered
  just by trying logins and reading the response — a well-known anti
  pattern. Both cases return `401 Incorrect email or password`.
- **Login uses form-encoded `OAuth2PasswordRequestForm`, not a JSON
  body**, unlike every other endpoint in this project. That's the shape
  FastAPI's built-in `OAuth2PasswordBearer` scheme expects — matching it is
  what makes the **Authorize** button in `/docs` work out of the box. A
  small inconsistency in request format for a real usability win during
  development; a real frontend would just POST that same form data from an
  HTML `<form>`.

## CI/CD (GitHub Actions)

`.github/workflows/ci.yml` runs on every push to `main` and every pull
request targeting `main`, as three jobs:

1. **Tests (pytest)** — starts real Postgres 16 and Redis 7 containers as
   job services, installs `requirements-dev.txt` on Python 3.11 (same as the
   Docker image), runs `pytest -v`. No `.env` needed: the service
   credentials match the defaults in `app/core/config.py`.
2. **Migrations (Alembic)** — runs `alembic upgrade head` on an empty
   database, `alembic check` (fails if models and migrations have drifted
   apart), then `downgrade base` + `upgrade head` again. The tests build
   their schema with `create_all`, so this is the only place the migration
   scripts themselves get exercised.
3. **Docker image** — runs only after 1 and 2 pass. Builds the image,
   smoke-tests it (`python -c "import app.main"` inside the container),
   and, on pushes to `main` only (never on pull requests), publishes it to
   GitHub Container Registry as `ghcr.io/<owner>/<repo>:latest` and
   `:sha-<commit>`.

Run the same checks locally before pushing:

```bash
pytest -v
docker compose exec api alembic check
docker build -t telemetry-api:local .
```

**Design notes**
- `permissions: contents: read` at the top, with `packages: write` granted
  only to the Docker job: a job gets the least access it needs.
- `concurrency` cancels an older run when you push again to the same
  branch, so CI minutes aren't spent on a commit that's already stale.
- The published image tag comes from `docker/metadata-action` because GHCR
  requires lowercase image names and this repo's name has capitals.
- Not included yet: automatic deployment. Publishing the image is the
  hand-off point; where it runs (a VM, Fly.io, ECS...) is a separate decision.

## Design decisions worth knowing about — testing

- **A dedicated `telemetry_test` database, created and torn down by the
  test suite itself, not your dev database.** The alternative — reusing
  the dev database and wrapping each test in a transaction that gets
  rolled back — is a legitimate pattern too, but it breaks down here
  because several endpoints call `db.commit()` explicitly mid-request (see
  `app/api/devices.py`, `app/ws/ingest.py`), and a commit inside a test's
  "outer" transaction can't be cleanly undone by rolling that transaction
  back afterward. A separate database sidesteps the problem entirely at
  the cost of a slightly slower setup step (session-scoped, so it's paid
  once per test run, not once per test).
- **`Base.metadata.create_all`, not Alembic, builds the test schema.**
  These integration tests exist to catch bugs in the application code —
  auth, pagination, fusion-on-ingest — against a schema that matches the
  current models. Whether `alembic upgrade head` from an empty database
  correctly reaches that same schema is a different, narrower question,
  worth its own (currently not written) migration test if this project's
  migration history ever gets complicated enough to need one.
- **Env vars are overridden at the very top of `conftest.py`, before any
  `app.*` import.** `app/db/session.py` and `app/db/redis.py` build their
  engine/client as module-level singletons the moment they're first
  imported — exactly once, like in production. Setting
  `POSTGRES_DB`/`REDIS_DB` even one import too late means those singletons
  already locked in the wrong (dev) target. This is also why the tests
  don't need to override FastAPI's `get_db` dependency: the engine itself
  points at the test database, so REST endpoints (`Depends(get_db)`) and
  the WebSocket endpoint (which imports `AsyncSessionLocal` directly) both
  transparently use it.
- **A manually-overridden, session-scoped `event_loop` fixture, instead of
  pytest-asyncio's per-test default.** The DB engine and Redis client are
  singletons with one connection pool each, for the whole process — just
  like in production. pytest-asyncio's default behavior hands every test
  function a *brand-new* event loop, but an asyncpg/redis connection is
  permanently bound to whatever loop created it; reusing a pooled
  connection under a different loop fails with "attached to a different
  loop" or "Event loop is closed." One shared loop for the whole session
  matches the "created once, reused everywhere" lifetime the engine
  already assumes.
- **WebSocket tests open their own `ws_capable_client()` per test, instead
  of sharing a fixture.** httpx-ws's `ASGIWebSocketTransport` opens an
  `anyio` task group that must be entered and exited by the *same* asyncio
  Task — but pytest-asyncio always runs a fixture's setup and its teardown
  as two separate Tasks, even at session scope. Opening and closing the
  transport entirely within one test function's `async with` block (one
  Task, start to finish) is what actually satisfies that constraint; see
  the comment above `ws_capable_client` in `tests/conftest.py` for the
  full trace of the error this avoids.
